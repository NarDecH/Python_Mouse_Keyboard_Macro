> สถานะ: **ชุด N1 (v2.5.4) และ N2 (v2.6.0) เสร็จแล้วทั้งคู่** — เงื่อนไขรวม `&&` และ

> feedback/ปัญหาจริงแจ้งได้ที่ [Issue #1](https://github.com/NarDecH/Python_Mouse_Keyboard_Macro/issues/1)

## 1. โจทย์

ปัจจุบัน (v2.5.3) ทุกเงื่อนไขทำงานแบบ **"ข้ามแถวตรง ๆ"**:

```text
แถว 1  If Image (btn.png)  Repeat = 5   ← ถ้าไม่เจอ ข้ามแถว 2–6
แถว 2  ...งานเมื่อเจอภาพ
...
แถว 6  Else If Image       Repeat = 3   ← ถ้ากลุ่ม A เล่นแล้ว ข้ามกลุ่ม B
```

จุดแข็ง: อ่านง่าย ตรวจสอบง่าย ไม่มี state ซ้อน
ข้อจำกัดที่ผู้ใช้ถามบ่อย:

1. **เงื่อนไขซ้อนเงื่อนไข** — "ถ้าภาพเจอ **และ** สีจุดถูก → ทำ A, ถ้าภาพเจอแต่สีผิด → ทำ B"
   ตอนนี้ทำได้แบบแผนภาพตัดสินแบน ๆ (แตกเป็น If หลายลำดับ) แต่สคริปต์ยาวและเดายาก
2. **ลูปย่อย** — "วนแถว 5–9 จนกว่าภาพจะเจอ (สูงสุด 10 รอบ)" ปัจจุบันต้องวนทั้งสคริปต์หรือใช้
   Repeat ของแถว (ทำซ้ำแถวเดียว ไม่ใช่ช่วงแถว)

## 3. แนวทางที่พิจารณา

### ทางเลือก A — บล็อกที่มีเครื่องหมายเปิด/ปิด (แนะนำ)

เพิ่ม Action 2 ตัวเป็นคู่เปิด-ปิด คล้ายหัวข้อ Section ที่มีอยู่แล้ว:

```text
แถว 1  🔷 Block Start (If Image btn.png)   Repeat = 0   ← เปิดบล็อก เงื่อนไขไม่จริง = กระโดดไป Block End
แถว 2  ...ทำ A
แถว 3  ...ทำ A
แถว 4  🔷 Block End                         ← ปิดบล็อก (ป้ายเท่านั้น ไม่เล่น)
```

- **เงื่อนไขซ้อนได้ตามธรรมชาติ** — Block Start ข้างในอีก Block Start ได้ (runner เก็บ stack)
- แถว Block Start ที่เงื่อนไข**ไม่จริง** = กระโดดข้ามไปที่ **Block End ที่จับคู่กัน** (นับวงเล็บ)
  ไม่ใช่ข้าม N แถวตายตัว → ผู้ใช้ไม่ต้องนับแถวเอง และแก้/แทรก/ลบแถวข้างในไม่มีผล
- **ลูปย่อย:** Block Start ตั้ง Additional เพิ่มได้ เช่น `until img.png` หรือ `max 10` =
  จบถึง Block End แล้วกระโดดกลับแถวเปิดบล็อก วนจนเงื่อนไขจริง/ครบ max
- GUI: สีแถวใหม่ (แถบฟ้าเข้ม?) + ย่อ/ขยายบล็อกได้ด้วยกลไก Section ที่มีอยู่ (_section_stash)
- CLI/`--validate`: นับเครื่องหมายเปิด/ปิดให้ครบก่อนเล่น (ปิดไม่ครบ = error ชัดเจนรายแถว)

ข้อเสีย: ต้องระวังผู้ใช้ลบ Block End ทิ้ง (ทางแก้: ลบเปิด/ปิดไม่ครบ → _validate เตือนก่อนเล่น,
เหมือนกลไก `_on_del_cleanup` ของกลุ่มย่อ)

### ทางเลือก B — เงื่อนไขรวม (AND/OR) ในแถวเดิม

ขยาย If Image/If Pixel ฯลฯ ให้ Additional ต่อท้าย `&&` / `||` ได้ เช่น
`btn.png && 300,300 #ffffff`

- ข้อดี: ไม่เพิ่ม Action ใหม่ กฎ Repeat เดิมใช้ต่อได้ทันที
- ข้อเสีย: แก้ปัญหาข้อ 1 เท่านั้น — **ไม่ได้ลูปย่อย** · Additional ยาวขึ้นจนอ่านยาก
- สรุป: เหมาะเป็น**ขั้นแรก** (จับคู่ง่าย ริสก์ต่ำ) ก่อนลงทางเลือก A

### ทางเลือก C — โหมดสคริปต์ล้วน (เขียน if/while จริง)

เพิ่ม Action "Python Block" รันโค้ดผู้ใช้

- ❌ ขัดหลักการ "ไม่มีโค้ด" + ความปลอดภัย (ผู้ใช้เผลอรันโค้ดอันตราย)
- ❌ ไฟล์สคริปต์แชร์กันอันตรายขึ้น — ตัดทิ้ง

## 4. แผนที่เสนอ (แบ่งเป็น 2 ชุดย่อย)

### ชุด N1 — เงื่อนไขรวม AND/OR (ขั้นแรก ริสก์ต่ำ) — ✅ เสร็จ v2.6.0

- ✅ `split_condition_and()` ใน macro_engine.py — แตก `&&` รองรับ timeout `Ns` ต่อชิ้น
  (ไม่ตัดค่าข้อความของ If Variable ที่ลงท้าย "5s")
- ✅ `ActionRunner.evaluate_if_var`/`evaluate_if_pixel` — ตัดสินเป็นค่าความจริง (ใช้ร่วมกันได้)
- ✅ IF_IMAGE/IF_PIXEL ใน `execute` + `evaluate_condition` (IF_VAR) รองรับ `&&` —
  mixed parts (ภาพ+สี+ตัวแปรในแถวเดียว) dispatch ต่อชิ้นถูกชนิด
- ✅ `validate_rows` ตรวจทุกชิ้นย่อย · เทสต์ TestN1AndConditions 10 ตัว (รวม 351 unit)
- OR (`||`) ยังไม่ทำ — รอความต้องการจริงจาก Issue #1

### ชุด N2 — Block Start/Block End (ลูปย่อย + ซ้อน) — ✅ เสร็จ v2.6.0

- ✅ Action ใหม่ 2 ตัว (`🔷 Block Start`/`🔷 Block End`) + ROW_STYLE หมวดใหม่ (block/blockend)
  + เมนูขวาแทรกบล็อก + hint ช่อง Additional
- ✅ `BlockRunner` ใน engine = หัวใจตัดสิน (goto, message) แหล่งเดียว — GUI/CLI หลัก/engine_cli
  ใช้ร่วมกัน · ตัวนับรอบลูปย่อย (dict แถวเปิด → รอบ) รีเซ็ตทุกรอบสคริปต์ ·
  STOP เช็ค stop_check ทุกจุดเดิมจึงหยุดได้ทุกชั้น · คีย์ค้างอยู่กับ release_all เหมือนเดิม
- ✅ Additional: `if ...` (ข้ามบล็อกเมื่อไม่จริง) / `until ...` (วนกลับจนจริง) / `max N`
  (จำกัดรอบ, ไม่ใส่ = 1000) · เงื่อนไขชุดเดียวกับ N1 + && ผสมได้ · ซ้อนได้ 8 ชั้น
- ✅ `--validate`: `validate_blocks()` ตรวจคู่เปิด/ปิด (นับวงเล็บ) + depth + Additional พัง
  รายแถว · ตอนเล่นจริงถ้าโครงสร้างพลาด = เล่นต่อตามลำดับ + เตือน (ไม่พังโปรแกรม)
- ✅ เทสต์: TestN2Blocks 12 ตัว (parser/จับคู่/ตัดสิน/validate/เล่นจริง GUI) +
  TestE2EBlocks 3 ตัว (CLI จริง: ข้ามบล็อก/นับ 5 รอบ/validate จับไม่ปิด) — รวม 373 unit + 15 E2E
- ย่อ/ขยายกลุ่มบล็อก (ต่อยอด `_section_stash`) ยังไม่ทำในรอบนี้ — ทำได้ภายหลังโดยไม่กระทบ engine

### สิ่งที่ห้ามลืม (จากบทเรียนเดิมของโปรเจกต์)

- แถวเงื่อนไขใหม่ต้อง `break`/`continue` **ก่อน do_step/ดีเลย์** เสมอ

## 6. ข้อเสนอเชิงเทคนิค OR (`||`) — รอโหวต ([Issue #9](https://github.com/NarDecH/Python_Mouse_Keyboard_Macro/issues/9))

> ข้อเสนอจากแผน v2.18 ข้อ 1 — **ยังไม่ลงมือ รอโหวต "ต้องมี" ก่อนเสมอ**
> (แผนหลักการ: ความซับซ้อน parser ต้องแลกด้วยความต้องการจริง)

### สัญญาที่ห้ามฝ่า (เหล็กเดิมทุกข้อ)
- สคริปต์เดิม (ไม่มี `||`) เล่นผลเดิม 100% — ไม่ใส่ `||` = เดิน parser เดิมทุกเส้นทาง
- กติกา skip เดิม: เงื่อนไขไม่จริง = ข้าม N แถว (N = Repeat) เหมือนเดิม — `||` ไม่แตะ
  กติกา skip×Block ของ v2.14.1 (หัวข้อ/บล็อกไม่กิน skip ฯลฯ)
- `&&` คงพฤติกรรมเดิมเป๊ะ — ตัวคั่นเสมอ ไม่มี escape

### Precedence — แตก `||` ก่อน แล้วแตก `&&` ภายในชิ้นย่อย
- `A || B && C` = **A หรือ (B และ C)** — `&&` แน่นกว่า `||` (ตรงตามภาษาโปรแกรมส่วนใหญ่
  และ AutoHotkey จึง export ตรง ๆ ได้) · ต้องการลำดับอื่นใช้ตัวแปรช่วยเหมือนกติกาปัจจุบัน
- engine ต่อยอด `split_condition_and()` เดิมด้วย `split_condition_or()` ใหม่: ตัด `>ชื่อ`/
  timeout token ก่อน (คงเดิม) → ตัด `||` ระดับบนสุด → แต่ละชิ้นเรียก `split_condition_and()`
- **Short-circuit:** ชิ้น `||` ใดจริง = นิพจน์จริงทันที ไม่ประเมินชิ้นถัดไป (ประหยัดค้นภาพ/
  ยิงเน็ต/วัด CPU ของชิ้นที่เหลือ) — ชิ้นที่ถูกข้ามรายงาน "ไม่ตรวจ (ข้ามสาย OR)" ใน dry-run

### จุดที่ต้องรับ `||` ครบ (เท่ากับจุดที่ `&&` อยู่วันนี้)
1. **แถวเงื่อนไขทุกชนิด** ใน `execute` — If Image/If Pixel/If Loop/If Time/If Variable +
   เงื่อนไข plugin (ผ่าน `match_condition_name`) — สายไหนไม่จริงก็ตามกติกาสายนั้นเดิม
2. **Block Start/End** (`if ...` / `until ...`) ผ่าน `evaluate_block_condition` แหล่งเดียว —
   แต่ละสาย (สี/ตัวแปร/plugin/ภาพ) ให้ OR ระดับบนสุดก่อน AND ภายในสาย
3. **validate_rows** — ชิ้นย่อยพังชิ้นไหนรายงานพร้อมลำดับชิ้น (เช่น "ชิ้น 2 ของ ||")
4. **dry-run** — เดิน short-circuit จริง เหมือนเล่นจริงทุกด้าน
5. **โทเคน `>ชื่อ`** เก็บผลเงื่อนไข — เก็บผลรวมนิพจน์ทั้งหมด (ตัดโทเคนก่อนแตก || เช่นเดิม)
6. **.ahk สองทิศ** — export: `||` แปลงตรง (AutoHotkey มี `&&`/`||` ตรง ๆ), import: รับ
   `||` ใน `if (n > 5 || n < 0)` กลับมาด้วย · บล็อกที่แปลไม่ได้ = comment ทั้งบล็อกเหมือนเดิม
7. สีแถว (row_tag cond) / ค้นหา / .ahk prescan — อ่านข้อความดิบ ไม่กระทบ

### ข้อควรระวังความเข้ากันได้
- `||` = ตัวคั่นเสมอ ไม่มีทาง escape — ข้อความจริงที่มีอักขระ `|` ต้องเลี่ยงไปใช้ตัวแปร
  (เหมือนกติกา `&&` ปัจจุบัน — ข้อความครอบ `""` ก็ยังแตกที่ตัวคั่น)
- สายตัวแปรล้วน `n > 5 || n < 0` — แตก `||` แล้วแต่ละชิ้นต้องไป `evaluate_if_var`
  ต่อชิ้น (จะไม่พังเพราะ `split_condition_and` ของชิ้นย่อยคืนลิสต์ว่าง)
- เงื่อนไข plugin กับ `||`: ชิ้นแรกตัดสินสายเหมือนเดิม — ชิ้นที่เหลือเช็คชื่อต่อเนื่อง
  (สาย plugin ผสมสายอื่นภายใน `||`/`&&` เดียวกันตามกติกา v2.13)

### ประมาณการ + แผนเทสต์
- engine: `split_condition_or` + ปรับ `evaluate_block_condition`/`execute` ~60 บรรทัด ·
  GUI ~10 บรรทัด (hint + เอกสาร) · .ahk สองทิศ ~15 บรรทัด
- เทสต์ TestOrConditions ~12 ตัว: parser/precedence/short-circuit/skip ครบทุกสาย/
  validate/dry-run/.ahk export+import/GUI Block Start — + E2E 1 ตัว
